# 会議フィードバック

文字起こしを「議事録」に変換するのではなく、会議の進め方と評価対象者の発言をコーチングする。断定ではなく、文字起こしに現れた観察事実と解釈を分け、次回に試せる小さな行動へつなげる。

## 進め方

### 1. 評価範囲とデータ品質を確定する

次の情報を文字起こしと依頼文から拾う。不足していても、分析可能な範囲で進め、推測で埋めない。

- 会議の目的、議題、期待される成果
- 評価対象者が誰か、会議での役割（司会、参加者、説明者など）
- 参加者と話者ラベルの対応（例: 自分=話者A）
- タイムスタンプの有無、発言の欠落や誤認識の可能性
- 今回とくに見たい観点（例: 話が長い、質問、合意形成、割り込み）

冒頭に、評価対象者と文字起こしの信頼度を短く記す。話者ラベルがない場合、または話者ラベルがあっても評価対象者との対応が不明な場合は、本人への評価を保留する。対応が確認できなければ、本人の発言セクションを「評価不可」と明記して省略し、会議全体の観察だけを返す。発言が途中で切れている、話者が混同されている、音声の抑揚が分からない場合も明記する。

会議の目的・期待成果が文字起こしや依頼文から分からない場合は、会議の有効性や「良い会議だったか」を断定しない。発言の明確さ、質問の構造、論点の反復など、観察できる会話上の特徴だけを評価し、目的が不明なため判断できない点を明記する。

### 2. 観察事実を時系列で抽出する

評価する前に、次のような観察をタイムスタンプ付き（存在する場合）で抜き出す。

- 会議の目的・論点・決定基準が提示されたか
- 議題間の移行、時間配分、脱線、同じ論点の反復があったか
- 質問、要約、確認、反対意見の扱いがどう行われたか
- 発言が一部の人に偏ったか、参加を促す場面があったか
- 決定、保留、担当者、期限、次の一歩が明確になったか
- 評価対象者の発言に、結論先行、理由、具体例、曖昧語、言い換え、割り込み、相手の発言の引用などがあったか

「観察事実」「そこから考えられる影響」「解釈・仮説」を分ける。たとえば「12:10〜14:00に同じ懸念が3回出た」は観察事実、「論点の収束が遅れた可能性がある」は解釈であり、同じ確度で扱わない。

### 3. 会議全体と本人の発言を別々に評価する

次の2つを混ぜない。

#### 会議全体の進行

- 目的・期待成果の共有
- 論点の整理と優先順位
- 時間・脱線・発言順のコントロール
- 傾聴、要約、異論の取り込み
- 意思決定の進め方と判断基準
- 参加者の巻き込みと発言の偏り
- 終了時の決定事項・未決事項・アクションの確認

#### 評価対象者本人の発言

- 要点の明確さと構造（結論、理由、具体例）
- 話の長さ、重複、前置き、曖昧語
- 質問の具体性と、相手の回答を受けた深掘り
- 相手の発言を受け止めてから自分の意見につなげているか
- 合意・反対・保留の表明の明確さ
- 発言のタイミング、割り込み、沈黙の扱い
- 目的に対する貢献と、相手が次に何をすればよいかの明確さ

会議全体の課題を、そのまま評価対象者本人の責任にしない。評価対象者が司会者・意思決定者でない場合は、「本人が次回変えられること」と「司会者・チームへの提案」を分け、本人が直接制御できない時間配分や議題設計を本人の改善点として扱わない。

発言量、発言回数、順番だけで貢献度や態度を判断しない。時間計測や発言比率を示すのは、話者ラベルとタイムスタンプが十分に信頼でき、かつ依頼に含まれる場合だけにする。示す場合も「文字起こし上の概算」とし、ランキングや性格診断にしない。

### 4. フィードバックを優先順位付けする

改善点を大量に並べず、会議の目的への影響が大きく、次回に行動で試せるものを2〜3件に絞る。各項目を次の形で書く。

```text
観察: 文字起こしで確認できる具体的な発言・流れ
影響: 会議の進行または相手の理解・参加に起きたこと
提案: 次回に取る具体的な行動
```

良かった点も、単なる称賛ではなく「何をしたか」「なぜ有効だったか」を書く。スコアは依頼された場合だけ出し、評価軸と根拠を併記する。根拠が少ないのに小数点付きの点数を付けない。

### 5. 次回の改善実験に落とす

改善点ごとに、次回1回で試せる行動を1つ提案する。次のように観察可能な形にする。

```text
会議の冒頭で、目的と今日決めることを30秒で宣言する。
論点が3往復したら、合意点・相違点・判断に必要な情報を要約する。
意見を述べる前に、相手の発言を一文で要約して確認する。
自分の説明は「結論→理由2つ→確認質問」で終える。
```

可能なら「成功のサイン」も付ける（例: 議題ごとに決定または保留理由が残る、同じ質問が繰り返されない、相手が次の行動を言い返せる）。一度に多くを直そうとせず、次回は最重要の1〜2個を選ぶ。

## 出力形式

依頼に別指定がなければ、次の形式で出力する。文字起こしの要約や議事録は、フィードバックの根拠として必要な分だけ含める。

```markdown
# 会議フィードバック

## 前提
- 評価対象者:
- 会議での役割:
- 文字起こしの信頼度と制約:
- 今回の評価範囲:

## 総評
会議の目的に照らした短い総評。断定できないことは仮説として書く。

## 役割に応じた改善範囲
- 本人が次回変えられること:
- 司会者・チームへの提案:

## 会議全体の進行
### 良かった点
- 観察 → 有効だった理由

### 改善すると効果が大きい点
1. 観察 / 影響 / 提案
2. 観察 / 影響 / 提案

## 評価対象者本人の発言
話者との対応が確認できた場合のみ記載する。対応不明の場合は「評価保留」とする。
### 良かった点
- 発言の具体例 → 良かった理由

### 改善すると効果が大きい点
1. 観察 / 影響 / 次回の言い換えまたは行動
2. 観察 / 影響 / 次回の言い換えまたは行動

## 次回に試すこと
- 行動:
- 成功のサイン:

## 根拠となる場面
- [時刻または発言位置] 観察事実

## 確認したいこと
- 文字起こしだけでは判断できず、本人に確認したい点
```

## フィードバックの原則

- 人格、能力、意図を断定せず、発言や会話の構造を扱う。
- 「感じが悪い」「リーダーシップがない」ではなく、観察可能な言動と会議への影響に言い換える。
- 文字起こしから声量、表情、沈黙の長さ、皮肉、緊張などを推測しない。分かる場合は音声・映像の情報源を明示する。
- 発言者が不明な文、認識誤りの可能性がある文、文脈が欠けた文を強い根拠にしない。
- 話者ラベルと評価対象者の対応が不明な場合、本人の発言・話し方・態度を推測して評価しない。
- 会議の目的が不明な場合、会議の有効性を断定せず、観察可能な会話上の特徴と判断保留を分けて書く。
- 評価対象者の役割外にある課題を本人の改善点にしない。「本人が変えられること」と「他者・チームへの提案」を分ける。
- 「もっと簡潔に」「よく聞く」のような抽象的な助言だけで終わらず、次回の言い方・タイミング・確認方法まで示す。
- 良い点と改善点の両方を示し、責任追及ではなく学習のための表現にする。
- 情報が足りないときは、結論を弱めるか確認質問を最後に置く。推測で参加者、意図、決定事項、担当者を埋めない。
- ユーザーが求めた場合だけ、会議の議事録・決定事項・アクション抽出を追加する。主成果物は会議フィードバックとする。

## 繰り返し利用する場合

前回のフィードバックや過去の文字起こしが渡された場合に限り、同じ会議種別・役割・評価軸で比較する。条件が異なる場合は単純比較せず、比較できない理由を明記する。改善した点、変化しなかった点、新しく現れたパターンを分け、前回の改善実験が実施されたかを確認する。過去資料がない場合は、今回をベースラインとして扱う。
