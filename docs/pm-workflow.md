# Engineering PM Workflow

このガイドは、要望を受けてから、仕様化、Issue化、優先順位付け、リリース、振り返りまでを一貫して扱うための、このリポジトリ専用の運用基準です。

## 出力の使い分け

| 段階 | 主に使うSkill | 成果物 |
|---|---|---|
| 要望整理 | `interview-me` | 目的、利用者、制約、成功指標、不明点 |
| 要件・仕様 | `spec-driven-development` | 仕様、前提、境界、テスト方針 |
| 計画 | `planning-and-task-breakdown` | Epic / Feature / Task、順序、依存関係、受入条件 |
| GitHub管理 | `github-to-tickets`, `github-triage` | Issue本文、ラベル、担当、ブロッカー、状態 |
| PM判断 | `prioritization-advisor`, `impediment-prioritization` | 判断軸、順位、理由、リスク |
| 品質・リリース | `shipping-and-launch` | テスト、監視、段階展開、ロールバック、確認項目 |
| 障害・改善 | `incident-postmortem` | 影響、時系列、要因、再発防止アクション |

## Issueの最小スキーマ

Epic、Feature、Task、Enabler、Testのいずれであっても、次の項目を埋める。該当しない項目は「該当なし」と明記する。

```text
種別: Epic | Feature | Task | Enabler | Test
タイトル:
目的・ユーザー価値:
スコープ:
非スコープ:
受入条件:
- Given / When / Then または検証可能な箇条書き
確認方法:
- コマンド、テスト、画面確認、ログ、メトリクスなど
依存Issue / 前提:
ブロッカー:
- 外部待ち / 社内判断待ち / 仕様待ち / なし
担当者:
優先度と理由:
対象リリース:
監視・ロールバック:
```

### ReadyとDone

タスクは、目的・スコープ・受入条件・確認方法・担当・依存関係が明らかになってからReadyとする。Doneは実装、レビュー、必要なテスト、受入条件の確認、関連ドキュメントの更新、リリース影響の確認が完了した状態とする。

## 依存関係と遅延リスク

依存関係は「Aが終わらないとBを開始できない」の形で書く。ブロッカーは次の3種類に分ける。

- 外部待ち: 顧客、ベンダー、外部サービス、審査などの返答待ち
- 社内判断待ち: プロダクト、法務、セキュリティ、運用などの意思決定待ち
- 仕様待ち: 要件、画面、API、データ、例外時の挙動などの確定待ち

遅延リスクは、発生してからではなく、計画時点で次の形式で登録する。

```text
リスク:
発生トリガー / 早期兆候:
影響: スコープ / 品質 / 期限 / コスト
発生確率: 低 / 中 / 高
担当者:
緩和策:
代替策・判断期限:
次回確認日:
```

## テスト計画の最低限

変更に応じて、Unit、Integration、E2E、性能・セキュリティ・アクセシビリティなどの非機能テストから必要なものを選ぶ。各テスト計画には、対象、環境、テストデータ、開始条件、終了条件、失敗時の対応を記録する。本番変更では、監視する指標、アラート、段階展開、ロールバック方法、リリース後の確認者も明記する。

## 会議メモの抽出形式

```text
決定事項:
- 決定内容 / 根拠 / 関係するIssue
未決事項:
- 論点 / 決める人 / 決定期限
アクション:
- 内容 / 担当者 / 期限 / 完了条件
ブロッカー:
- 種類（外部待ち・社内判断待ち・仕様待ち）/ 解消条件
次回確認:
- 日時 / 確認する指標 / 参加者
```

## このリポジトリで使えるプロンプト例

### 新機能の要件整理

```text
新機能「チーム別の利用状況レポート」を検討したい。
誰のどんな問題を解くのか、成功指標、制約、非スコープ、不明点を一問ずつ確認して。
前提を勝手に埋めず、最後にPRDのたたき台と未決事項を出して。
```

### 機能をGitHub Issueへ分解

```text
この仕様をEpic・Feature・Task・Testに分解して。
各Issueに目的、スコープ、受入条件、確認方法、担当候補、依存Issue、
「外部待ち／社内判断待ち／仕様待ち」のブロッカー分類、優先度を付けて。
まずIssue案をレビュー用に出し、私が承認するまでGitHubへ登録しないで。
```

### 遅延リスクの洗い出し

```text
次の計画について、期限遅延につながるリスクを早期兆候付きで洗い出して。
各リスクに影響、発生確率、担当者、緩和策、代替策、判断期限、次回確認日を付け、
外部待ち・社内判断待ち・仕様待ちを区別して。
```

### リリース前チェック

```text
この変更の本番リリース前チェックを作って。
テスト結果、監視とアラート、段階展開、データ移行、権限・セキュリティ、
ロールバック条件と手順、リリース後の確認項目を含め、未確認項目は残課題として分けて。
```

### 障害後の振り返り

```text
次の障害情報から、責任追及をしないポストモーテムを作って。
影響、検知から復旧までの時系列、根本原因と寄与要因、検知・対応の改善、
再発防止アクション（担当者、期限、完了条件、優先度）を整理し、情報不足は質問して。
```

### 会議メモからアクション抽出

```text
次の会議メモから、決定事項、未決事項、アクション、担当者、期限、
外部待ち・社内判断待ち・仕様待ちのブロッカー、次回確認事項を抽出して。
担当者や期限が書かれていない項目は推測せず「未定」として、確認質問を最後に出して。
```
